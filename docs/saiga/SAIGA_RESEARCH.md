# Локальные языковые модели как агенты и NPC в Space Station 14

**Исследовательский журнал проекта «Сайга»**
Форк: Monolith (Forge-Station/Monolith) · Движок: RobustToolbox 277 · .NET 10
Модель: `saiga_gemma2_9b` (Q4_K_M, ~5.8 ГБ) через Ollama · Железо: AMD Ryzen 5 8400F, RTX 5060 8 ГБ, 15 ГБ RAM
(ранее `saiga_llama3_8b`; перешли на 9B ради удержания контекста)

---

## Аннотация

Работа исследует, как подключить **локальную** языковую модель (LLM) к многопользовательской
игре Space Station 14 для двух задач: (1) разговорные NPC и (2) ИИ-агент, управляющий
персонажем-игроком. Ключевая инженерная идея — **разделение труда между LLM и нативным
ИИ игры**: «думание» и речь делает нейросеть (GPU, только в момент реплики), а перемещение и
рутинное поведение — встроенный движок NPC (HTN, pathfinding, CPU). Это позволяет держать
живых персонажей при минимальной нагрузке на видеокарту.

---

## 1. Мотивация и вопросы исследования

- **RQ1.** Можно ли интегрировать локальную LLM в сетевую игру так, чтобы это не нарушало
  доверие/детерминизм мультиплеера?
- **RQ2.** Где должны проходить вычисления (сервер / клиент / отдельный хост) и как это влияет
  на нагрузку GPU?
- **RQ3.** Насколько разумно разделить «высокоуровневые решения» (LLM) и «низкоуровневое
  поведение» (нативный HTN-ИИ игры)?
- **RQ4.** Какова субъективная связность диалога у 8B-модели Q4 при ограниченном контексте
  (восприятие сцены + память диалога)?

## 2. Системная архитектура

```
                 ┌─────────────────────────┐
   речь рядом →  │  Сервер SS14 (CPU)       │
                 │  • SaigaManager → HTTP   │ ── POST /api/chat ──▶ Ollama (GPU)
                 │  • SaigaNpcSystem (NPC)  │ ◀── JSON {say,action} ──
                 │  • SaigaAgentBrainSystem │
                 │  • HTN / pathfinding     │
                 └────────────┬────────────┘
                              │ сетевые события
                 ┌────────────┴────────────┐
                 │  Клиент(ы) SS14          │
                 │  • SaigaAgentSystem      │  движение через incmd (steering)
                 └─────────────────────────┘
```

Исследованы **две схемы**:

| Схема | Кто управляет | Движение | Диалог | GPU |
|---|---|---|---|---|
| **A. Серверный NPC** | движок (HTN) | навигация (CPU) | `SaigaNpc` | только на речь |
| **B. Клиент-агент** | второй клиент-игрок | steering на клиенте | через серверный «мозг» | только на речь |

## 3. Реализованные компоненты

**Shared** (`Content.Shared/_Mono/Saiga/`)
- `SaigaCVars` — конфигурация (URL, модель, таймаут, температура; клиентские `saiga.agent.*`).
- `SaigaAgentEvents` — сетевые события запрос/ответ решения (sandbox-safe).

**Server** (`Content.Server/_Mono/Saiga/`)
- `SaigaManager` — HTTP-клиент к Ollama (`/api/chat`, поддержка `format:json`).
- `SaigaNpcComponent/System` — NPC слышит речь (`ListenEvent`), отвечает с памятью диалога,
  по команде включает следование/остановку через blackboard HTN.
- `SaigaAgentBrainSystem` + `SaigaAgentStateComponent` — «мозг» для клиент-агента: восприятие
  сцены + услышанное + история → решение `{say, action, target}`.
- `SaigaTaoAppearanceComponent/System` — применяет фиксированный профиль персонажа на спавне.

**Client** (`Content.Client/_Mono/SaigaAgent/`)
- `SaigaAgentSystem` — цикл агента: запрос решения у сервера → речь (`say`) и непрерывное
  следование к цели удержанием клавиш (`incmd`).
- `SaigaAgentCommand` — `saiga_agent on|off|goal <текст>`.

**Прототипы** (`Resources/Prototypes/_Mono/`)
- `PersonalAISaiga` — pAI-устройство с диалогом Сайги.
- `MobSaigaTao` — гуманоид «Цзинъи Тао»: облик из профиля + HTN + диалог.
- `SaigaBehaviorCompound` — HTN: следовать-если-есть-цель, иначе бездействовать.

## 4. Ключевые инженерные находки

1. **Сервер не в песочнице, клиент — в песочнице.** Серверный контент может использовать
   `System.Net.Http`/`System.Text.Json`; клиентский — нет (проверка `res.typecheck` на старте).
   → Весь HTTP/JSON держим на сервере; клиент общается с ним сетевыми событиями.
2. **`RobustSynchronizationContext`.** `await` в обработчике события возвращает продолжение на
   главный игровой поток — после запроса к Ollama можно безопасно трогать симуляцию.
3. **Разделение LLM ↔ HTN.** Нативный NPC-ИИ (HTN, `FollowCompound`/`IdleCompound`,
   pathfinding) даёт движение на CPU; LLM нужен лишь для решения «следовать/стоять» и речи.
   Видеокарта простаивает, пока никто не разговаривает.
4. **Управление игроком через клиент.** Движение персонажа воспроизводится консольной
   командой `incmd <MoveDir> Down/Up` — подтверждено, что работает. На этом построен
   непрерывный steering к цели.
5. **Конфликт «вселение vs NPC-ИИ».** Если игрок вселяется в NPC, нативный HTN и `SaigaNpc`
   отключаются (мобом управляет игрок). Схемы A и B нельзя смешивать на одной сущности.
6. **Совместимость профилей персонажей.** Импорт из чужого форка падает из-за отсутствующих
   прототипов (маркинги/лоадауты/антаги) и из-за того, что `hairColor` в этом форке —
   список, а не скаляр. Решение — очищенный профиль только с валидными полями.

## 5. Методология (наблюдения)

Текущая стадия — **поисковая инженерная разработка** с качественными наблюдениями, а не
контролируемый эксперимент. Логирование решений добавлено в `saiga.agent`/`saiga.npc`
(строки вида `heard=[...] -> say="..." action=...`).

**Сбор метрик (CSV).** Задай CVar `saiga.metrics_path` — и каждый запрос к модели пишет строку в файл:

```
cvar saiga.metrics_path "/tmp/saiga_metrics.csv"
```

Колонки: `time_iso, source (npc|agent), model, latency_ms, total_ms, prompt_tokens,
eval_tokens, tokens_per_sec, json_format, json_valid, reply_chars, ok`.
Этого достаточно для метрик §7: латентность (p50/p95 по `latency_ms`), пропускная
способность (`tokens_per_sec`), доля валидного JSON (`json_valid`), доля успешных (`ok`).

**Транскрипт диалогов и действий (JSONL).** Задай CVar `saiga.transcript_path` — система сама
ведёт полную историю взаимодействий (по строке-объекту на реплику):

```
cvar saiga.transcript_path "/tmp/saiga_transcript.jsonl"
```

Поля: `time, source, speaker, heard, say, action, target`. Это сырьё для качественного
анализа диалога, разметки «по делу/не по делу» и трассировки решений follow/stop.

**Качественные наблюдения:**
- Латентность ответа модели: ~0.4–0.7 с на запрос (короткие реплики, 8B Q4, GPU).
- Диалог становится связным при подаче в контекст «услышанного» + истории; без этого модель
  выдаёт дежурные фразы.
- Мусорная цель (число вместо текста) ломает поведение → добавлена защита-санитайзер.
- Steering без pathfinding достаточно для открытых помещений, упирается в стены в узких.

## 6. Ограничения

- Нет обхода препятствий у клиент-агента (steering, не pathfinding).
- 8B Q4 ограничена в рассуждениях; нет инструментов/долговременной памяти между раундами.
- Один Ollama-инстанс — конкурентные запросы выстраиваются в очередь; на 8 ГБ VRAM число
  одновременно «думающих» агентов ограничено.
- Нет защиты от инъекций промпта через внутриигровой чат.

## 7. План настоящего эксперимента (следующий этап)

Чтобы превратить это в измеримое исследование, предлагается:

1. **Метрики.** Латентность (p50/p95), доля валидного JSON, доля «по делу» ответов
   (ручная разметка), успех выполнения команд (follow/stop), нагрузка GPU/VRAM, токены/с.
2. **Условия (A/B).** Сравнить: (a) без контекста сцены, (b) +услышанное, (c) +история,
   (d) +RAG по лору станции. Гипотеза: связность и уместность растут c→d.
3. **Модели.** Сравнить saiga_llama3_8b Q4 vs Q8 vs более лёгкая модель для NPC.
4. **Размещение вычислений.** Локальный Ollama vs выделенный GPU-хост (смена `saiga.api_url`) —
   влияние на тик сервера и FPS клиента.
5. **Масштаб.** Кривая деградации латентности от числа одновременных агентов.
6. **Воспроизводимость.** Зафиксировать сиды, промпты, версию модели, конфиг.

## 7a. Дорожная карта (обсуждено, не реализовано)

- **Децентрализованный инференс (per-player endpoint).** Сервер только оркестрирует
  (восприятие + промпт + async HTTP), а сам инференс идёт на **машину игрока**: клиент при
  включении агента передаёт серверу свой Ollama-endpoint, сервер шлёт запросы туда.
  Свойства: на сервере нет модели и GPU-нагрузки; масштабируется на много ИИ (каждый игрок
  приносит своё железо, нет общей очереди). Нужны: лимит активных агентов на сервере,
  кулдауны, туннель до Ollama игрока. Это аргумент для админов чужих сборок: «чем больше ИИ,
  тем больше вычислений приносят сами игроки; сервер только форвардит под лимитом».
- **Запуск на чужом сервере** — только с разрешения админов (мёрж кода) + per-player endpoint.
  Бот на неавторизованных публичных серверах = нарушение правил (бан), не делаем.
- **Автономный цикл целей** («осмотрелся → выбрал цель → действует») — отдельная большая ветка
  поверх реактивного агента.
- **Go-to точка/предмет** + локальный обход стен на клиенте (в работе).

## 8. Как воспроизвести

```fish
# 1. Ollama с моделью
ollama serve   # или systemctl; модель: bambucha/saiga-llama3
# 2. Сервер (мозг + NPC), запись лога
cd /home/krovin/Monolith; dotnet run --project Content.Server -- --cvar saiga.enabled=true | tee /tmp/srv.log
# 3. Клиент(ы)
dotnet run --project Content.Client -- --connect --username Krovin
dotnet run --project Content.Client -- --connect --username SaigaAI   # для схемы B
```

Спавн-сущности: `MobSaigaTao` («Цзинъи Тао»), `PersonalAISaiga` («Сайга»).
Команды клиент-агента: `saiga_agent on | off | goal <текст>`.
