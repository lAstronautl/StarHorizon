# dmm2yml — конвертер карт SS13 → SS14

Переносит карты из BYOND/SS13 (`.dmm`, обычный формат и TGM) в формат карт
SS14 (`.yml`, `format: 7`).

Системы сущностей у игр разные, поэтому конвертер **никогда не догадывается**.
Всё, для чего нет правила, попадает в таблицу, а `convert` отказывается делать
карту, пока в таблице есть незаполненные строки. Решение о каждой замене
принимает человек — в том числе решение «выбросить».

Нужен только Python 3.11+ и PyYAML. Сборка проекта и сабмодуль RobustToolbox
не требуются.

## Как пользоваться

```bash
# 1. Что не сопоставлено
python3 Tools/dmm2yml/dmm2yml.py scan MetaStation.dmm -o metastation.todo.csv

# 2. Открыть CSV в Excel/LibreOffice и заполнить колонку ss14_id

# 3. Собрать карту
python3 Tools/dmm2yml/dmm2yml.py convert MetaStation.dmm \
        --table metastation.todo.csv -o metastation.yml

# 4. (необязательно) Закрепить решения для следующих карт
python3 Tools/dmm2yml/dmm2yml.py merge metastation.todo.csv
```

`scan` на станции 255×255 занимает пару секунд, `convert` — около минуты.

## Каталог по всему апстриму (`catalog`)

`scan` показывает, чего не хватает для одной карты. `catalog` делает то же самое
сразу для нескольких — или для целого дерева каталогов с `.dmm`:

```bash
python3 Tools/dmm2yml/dmm2yml.py catalog путь/к/tgstation/_maps/map_files -o catalog.csv
# или явным списком:
python3 Tools/dmm2yml/dmm2yml.py catalog Meta.dmm Delta.dmm Kilo.dmm -o catalog.csv
```

Строки суммируются по всем картам (один путь SS13 — одна строка, `count` —
сумма по всем файлам), а `example` показывает, на какой конкретно карте и по
каким координатам смотреть. Это даёт список, отсортированный по тому, что
реально нужно чаще всего, а не по тому, что попалось на одной случайной карте.

Прогон по семи станциям текущего апстрима tgstation (`CatwalkStation`,
`Deltastation`, `IceBoxStation`, `KiloStation`, `MetaStation`, `NebulaStation`,
`tramstation` — актуальная ротация карт, `_maps/*.json`) даёт ~1.02 млн атомов,
из них 284 603 без правила по 4400 уникальным путям. Верхние 300 строк
закрывают 88% этого объёма — это и есть практический список для дозаполнения,
не 4400 записей разом.

**Что не пытался угадать, и почему:**

* **`/turf/open/genturf`, `/turf/closed/mineral/random/*`, `/turf/open/openspace`,
  варианты `/turf/open/misc/asteroid/*`, `/turf/open/lava/*`** — верхушка списка
  по объёму (более 200 000 атомов). У них нет статичного эквивалента: `genturf`
  генерирует ландшафт процедурно во время игры, `mineral/random` заранее
  неизвестно каким будет (случайная руда), `openspace` — провал на нижний
  z-уровень. Втиснуть их в один тайл — не перевод, а потеря игровой механики;
  решение, каким тайлом жертвовать, — не моё.
* **`/obj/effect/landmark/start/<профессия>`** (точки спавна по должностям,
  ~2700 атомов) — в SS14 это тоже `SpawnPoint`, но один прототип на профессию
  (`SpawnPointCargoTechnician`, `SpawnPointQuartermaster`, …), и список
  профессий у tgstation и у этого форка не совпадает один в один. Правильное
  сопоставление — отдельная задача по всем ролям, а не одна строка словаря;
  здесь её нет, чтобы не подставить экипаж не на те точки спавна молча.
* **`/obj/effect/landmark/*` и `/obj/effect/spawner/*` в остальном** — тоже не
  тронуты целиком: часть путей в этих деревьях уже размечена в `entities.yml`
  (например, заспавнер окон), и групповое правило `ignore` перекрыло бы их —
  `ignore.yml` матчится по префиксу так же, как обычные правила, без учёта того,
  что где-то внутри дерева есть более точное исключение.

**Что добавлено по итогам прогона**, каждое — проверенное решение, а не догадка:

* `/obj/effect/mapping_helpers` → `ignore.yml`. Это служебные объекты
  разметки (задают доступ шлюзу, ломают пол, подключают датчик атмосферы) —
  в `code/modules/mapping/mapping_helpers.dm` каждый вызывает `qdel(src)`
  сразу после применения эффекта и никогда не отрисовывается.
* `/obj/machinery/newscaster`, `/obj/machinery/navbeacon`,
  `/obj/machinery/status_display` → `ignore.yml`. Проверено по
  `Resources/Prototypes`: этих трёх систем в этом форке SS14 просто нет —
  не переименованы, не спрятаны, отсутствуют как класс.
* Декали `trimline/dark` и `trimline/dark_blue` → `decals.yml`. Существующий
  генератор уже покрывал эти цвета для `tile/*`, но не для `trimline/*` —
  механическое расширение той же таблицы, все id проверены по индексу.

## Дозаполнение хвоста (предметы/мебель/машины)

По итогам каталога дозаполнил `entities.yml`: около 100 новых правил для самых
частых предметов, мебели и машин из хвоста списка — ручки, инструменты,
аптечки, кровати, зеркала, шкафы, факсы, вендинги и т.д. Каждый id проверен по
`Resources/Prototypes`, ничего не угадано. Ещё 12 путей (`light_switch`,
`requests_console`, `digital_clock`, `photocopier`, `iv_drip`, `shower`,
`ladder`, `transit_tube`, `transport/linear`, `marker_beacon`, `pai_card`,
`newspaper`) добавлены в `ignore.yml` — тем же способом, что и newscaster
раньше: проверено с нескольких сторон (точный id, поиск по ключевым словам,
прямой grep), в этом форке SS14 их действительно нет.

На семи станциях апстрима это дало 4607 → 4057 непокрытых путей. На самой
`MetaStation.dmm` — 2005 → 1635.

**По ходу дела нашлись и исправлены две настоящие ошибки, не связанные с
дозаполнением само по себе:**

* **Индекс прототипов пропускал часть файла.**
  `Entities/Structures/Furniture/sink.yml` — единственный файл в репозитории,
  где список начинается не с нулевого отступа (по YAML это законно, отступ
  просто должен быть *согласованным*, а не нулевым). Парсер ожидал ровно
  2 пробела перед `id:`, поэтому все пять прототипов раковин, включая сам
  `Sink`, были невидимы для инструмента. Теперь отступ поля определяется
  относительно отступа самого `- type:`, а не считается нулевым.
* **Двоеточие в имени объекта ломало карту.** Название вида
  `Danger: Conveyor Access` (реальное имя из MetaStation) писалось в YAML без
  кавычек — строка `name: Danger: Conveyor Access` парсится как вложенный
  словарь, а не как текст, и весь файл переставал грузиться. Теперь имя
  сущности проходит через тот же экранирующий вызов PyYAML, что и остальной
  YAML-вывод (кавычки только когда действительно нужны, в одинарных кавычках —
  так же, как уже делалось для `color`).

Обе ошибки закрыты проверками в `selftest` (`dictionaries: indented prototype
lists`, `rendering: entity names quote safely`), каждая проверена на то, что
падает при откате исправления.

**Отдельная находка, которую я не стал исправлять молча.** Хотел добавить
`onWall` для базового `/obj/machinery/button/door` (без `/directional`),
рассудив, что раз есть переменная `dir`, можно определить стену динамически —
как уже работает для `SignalButtonDirectional`. Проверка на реальной карте
показала: 14 из 18 экземпляров вообще не имеют `dir` в `.dmm`, и кнопка
сдвигалась в сторону, где стены чаще всего нет. Правило исправлено обратно на
простое размещение без сдвига — статистика по одной карте лежит в README как
причина, почему тут нет `onWall`.

## Случайные спавнеры

Отдельная категория из каталога — `/obj/effect/spawner/random/*`
(200 путей, 3978 атомов). Это не единичный «непонятный предмет», а система:
SS13 при старте карты выбирает один предмет из взвешенной таблицы и удаляет
спавнер. Подставить сюда один конкретный предмет значило бы соврать про
случайность — та же проблема, что с `genturf`.

Но у SS14 есть **своя точно такая же система**:
`Resources/Prototypes/Entities/Markers/Spawners/Random/*` — маркер с
компонентом `RandomSpawner`/`EntityTableSpawner`, который тоже выбирает один
предмет из своей таблицы и удаляет себя. Поэтому здесь сопоставление идёт не
предмет к предмету, а **таблица к таблице**: `/obj/effect/spawner/random/trash`
→ `RandomSpawner` (маркер, ссылающийся на `GenericTrashItems`),
`/obj/effect/spawner/random/vending/colavend` → `RandomVendingDrinks` и т.д.
26 правил, каждое — сверенный по содержимому реальной SS14-таблицы, а не по
совпадению имени. Суффиксы вида `/two`, `/three`, `/no_decals` (SS13-способ
сказать «бросить кубик ещё раз») подхватываются тем же наследованием по
дереву путей, что и везде — отдельная запись под каждый суффикс не нужна.

На семи станциях апстрима это закрыло 3978 → 1637 атомов случайных спавнеров
(59%). Остальное — либо не имеет содержательного аналога в SS14
(`aimodule/*`, `techstorage/*` — специфичные для tgstation системы), либо я не
нашёл таблицу с уверенностью (`clothing/costume`, `entertainment/dice`,
`bureaucracy/briefcase`) и не стал подставлять наугад — они остаются в отчёте.

## Окно

Всё то же самое, но без Excel:

```bash
python3 Tools/dmm2yml/dmm2yml.py gui
# Windows, чтобы не висело чёрное окно консоли:
pythonw Tools\dmm2yml\dmm2yml.py gui
```

Tkinter входит в состав Python на Windows, ставить ничего не нужно.

Порядок тот же: выбрать `.dmm` → «Разобрать карту» → заполнить колонку «замена в
SS14» → «Собрать карту». Кнопка «Сохранить в словари» закрепляет решения для
следующих карт, «Открыть/Сохранить таблицу» — обмен теми же CSV, что понимает
командная строка, так что начать можно в окне и доделать в Excel или наоборот.

Что окно даёт сверх CSV:

* **Автодополнение** — двойной клик по строке, и id подсказывается по живому
  индексу `Resources/Prototypes`. Стрелки выбирают, Enter подставляет.
* **Проверка на лету** — введённый id подсвечивается зелёным, если такой
  прототип есть, красным, если нет, серым для `skip`. Опечатку видно сразу, а не
  на этапе сборки.
* **Фильтр и сортировка** — по любой колонке; строки идут по убыванию частоты,
  так что сверху то, что даёт больше всего карты за меньше всего работы.
* **Массовые действия** — выделить несколько строк и разом пометить `skip`,
  подставить подсказку или очистить.

Автодополнение в окне намеренно шире, чем колонка `suggestion` в CSV: там
показывается только уверенное совпадение, потому что оно записывается как ответ,
а в списке можно показать всё, что содержит введённое, — человек его читает и
выбирает сам.

### Колонки таблицы

| колонка | что значит |
|---|---|
| `dmm_path` | путь SS13, ключ строки |
| `kind` | `turf` / `decal` / `entity` — определяется автоматически |
| `count` | сколько раз встречается на карте |
| `example` | координаты одного экземпляра, чтобы найти его в редакторе |
| `suggestion` | подсказка, **только** точное или префиксное совпадение по имени; пусто = уверенного варианта нет |
| `ss14_id` | **заполняете вы.** id прототипа SS14 |
| `color` | для декалей, `#RRGGBBAA` |
| `notes` | переменные, встреченные у этого пути (`dir`, `name`, …) |

В `ss14_id` можно писать:

* `WallSolid` — один прототип;
* `Grille+ReinforcedWindow` — несколько сущностей на одной клетке;
* `FloorSteel+Table` — для `turf`: тайл и стоящая на нём сущность;
* `skip` — выбросить осознанно.

Пусто оставлять нельзя: именно на пустых строках `convert` останавливается.
Каждый непустой id проверяется по `Resources/Prototypes` — опечатка или
несуществующий прототип останавливают конвертацию так же, как пустая строка.

## Словари

Постоянные правила лежат в `mapping/` в YAML: там нужна вложенность, которую
CSV не выражает (тайл и сущность на одной клетке, разные id по направлению,
цвет). CSV — только для разовой дозаполнялки.

| файл | о чём |
|---|---|
| `turfs.yml` | `/turf/...` → тайл, для стен ещё и сущность |
| `decals.yml` | `/obj/effect/turf_decal/...` и `/obj/effect/decal/...` → декали |
| `entities.yml` | `/obj/...`, `/mob/...` → прототипы |
| `ignore.yml` | пути, выбрасываемые намеренно (по умолчанию — `/area`) |
| `grid_template.yml` | компоненты map- и grid-сущности готовой карты |

Правила **наследуются вниз по дереву путей**: правило для
`/turf/open/floor/iron/dark` покрывает и `/dark/corner`, и `/dark/textured`, и
`/dark/smooth_half`. Так 350 правил закрывают около 91% атомов станции /tg/.
Точное совпадение всегда важнее унаследованного. Общих правил-заглушек вроде
`/obj: SomeEntity` в словарях нет намеренно — иначе смысл таблицы теряется.

### Позиция настенных приборов: `onWall`

Мало́ разницы, объект просто смотрит на север или висит на северной стене
(`dir` против `wall`, ниже) — есть ещё разница, **на какой клетке** он в итоге
окажется. SS13 всегда кладёт настенный прибор на клетку пола перед стеной. SS14
для части приборов делает иначе — кладёт прямо **на клетку самой стены**:
проверено на `Resources/Maps/amber.yml`, где 100% `AirAlarm`, `APCBasic`,
`FireAlarm`, огнетушителей, интеркомов и кнопок дверей делят клетку с
`WallSolid`, и 0% стоят на соседней. Лампы и камеры, наоборот, всегда остаются
на полу, как и в SS13.

Флаг `onWall: true` в правиле — это перенос на клетку стены в дополнение к
повороту. Ставится вместе с `wall:` для семи прототипов, у которых это
подтверждено (`entities.yml`); для ламп, камер и окон его нет. Без него
настенные приборы после конвертации выглядят оторванными от стены и стоящими
посреди комнаты — раньше конвертер именно так и делал.

### Направление: `dir` против `wall`

SS13 прячет ориентацию части объектов в самом пути, и означает она две разные
вещи:

* `wall: north` — объект висит на стене с севера, значит в SS14 он **смотрит на
  юг**, от неё. Так помечены светильники, воздушные сигнализации, камеры, APC,
  направленные окна.
* `dir: 1` — объект просто смотрит на север. Так помечены отдельно стоящие
  вещи вроде табуретов.

Перепутать их — значит развернуть половину карты на 180°.

## Что стоит проверить глазами после конвертации

* **Повороты угловых декалей.** Направление декали в SS13 живёт в `dir`, а в
  SS14 — в самом id (`QuarterTileOverlayGreyscale90`). Соответствие
  (`N` → база, `E` → 90, `S` → 180, `W` → 270) внутри себя непротиворечиво, но
  по спрайтам не сверялось. Если углы повёрнуты — правится в `decals.yml`
  в одном месте, и все плитки следуют за ним.
* **Окна над космосом.** В SS13 внешние окна стоят прямо на космосе; в SS14 под
  ними обычно нужен пол или решётка. Конвертер тайлы сам не дорисовывает.
* **Труб и кабелей в результате нет.** Сети атмоса и питания у SS13 и SS14
  устроены слишком по-разному, чтобы перенос был полезен: у труб не переживают
  слои, цвета и направления, а кабельную сеть всё равно надо перекладывать под
  модель питания SS14. Поэтому они выброшены (`mapping/ignore.yml`) — на
  MetaStation это около трети всех объектов: 5857 труб и 3631 кабель. Машины,
  которые на этих сетях стоят (вентиляция, скрубберы, насосы), переносятся, их
  остаётся только соединить.
* **Диагональные направления.** `dir` 5/6/9/10 сводятся к одной кардинальной
  составляющей — в SS14 диагональных поворотов у большинства сущностей нет.
* **Разделение грида.** SS14 грузит каждый несвязный участок тайлов как отдельный
  грид. Это нормально, но чтобы не увидеть это впервые в логе сервера, `convert`
  сам сообщает число таких участков и где находятся мелкие.
* **Переменные, кроме `dir` и `name`.** Отбрасываются: `pixel_x/y`, `req_access`,
  `c_tag`, `network` и ещё около 75 других. Какие именно встретились у пути,
  видно в колонке `notes`.

## Куда класть результат

**Не в `Resources/Maps/`**, пока карта не доделана.
`Content.IntegrationTests/Tests/PostMapInitTest.cs` перечисляет через
`ContentFindFiles` *все* файлы под `/Maps/` и пытается их загрузить, так что
недоделанная карта уронит CI.

Готовая карта — обычный `format: 7`: открывается редактором карт SS14, и после
пересохранения даёт минимальный diff, потому что конвертер пишет YAML в том же
виде, в каком его пишет сам SS14.

## Тесты

```bash
python3 Tools/dmm2yml/dmm2yml.py selftest
```

Одиннадцать проверок, каждая — на ошибку, которая уже была допущена хотя бы раз:

```
  [ok  ] parser: geometry and vars         2x4, top-down rows, dir parsed
  [ok  ] rules: exact, inherited, ignored  all four behave
  [ok  ] problems: one line per path       3 unresolved paths, 3 lines
  [ok  ] orientation: wall vs dir          wall inverts, dir does not
  [ok  ] chunks: cell indexing             6 probes, negative chunks, variant and rotation kept
  [ok  ] chunks: no empty chunks           1 chunk(s) written, the all-Space one dropped
  [ok  ] chunks: round-trip vs repo maps   994/994 byte-identical across 60 maps
  [ok  ] dictionaries: ids resolve         359 rules, every id exists
  [ok  ] conversion: fixture map           tiles, entities, rotation, decal
  [ok  ] rendering: valid map document     5 entities, uids unique
  [ok  ] template: components load bare    11 bare components, all seen bare in real maps
```

Что именно ловится:

* **parser** — ориентация сетки `.dmm`: строки идут сверху вниз, колонки не
  перепутаны с рядами, переменные вроде `dir = 4` разбираются.
* **rules** — точное правило, унаследованное правило (побеждает более длинный
  родитель), `ignore`, и что неизвестный путь ни во что не превращается.
* **orientation** — `wall` инвертирует направление, `dir` нет, и все четыре
  поворота совпадают с теми, что выведены по `Resources/Maps/amber.yml`.
* **chunks: cell indexing** — тайл попадает в ту клетку, куда положен (включая
  отрицательные чанки), и не теряет `variant` и `rotationMirroring`.
* **problems: one line per path** — путь без решения попадает в отчёт один раз.
  Он находится дважды (пустая строка таблицы и нерешённый путь при обходе), и
  сложение двух списков однажды дало «4051 путь» там, где их было 2026.
* **chunks: no empty chunks** — чанк, в котором только космос, не пишется вовсе.
  Космос — такой же тайл словаря, и без этого станция посреди карты 255×255 тащит
  за собой сотню чанков пустоты, на каждый из которых движок ругается.
* **chunks: round-trip** — чанки всех карт формата 7 из `Resources/Maps`
  перекодируются побайтово одинаково.
* **dictionaries** — каждый id из `mapping/*.yml` существует в
  `Resources/Prototypes`. Это ловит переименование прототипа в апстриме.
* **conversion** — крошечная карта из `selftest.py` (2×4 клетки) превращается
  ровно в то, что расписано там же руками: тайлы, стена, поворот настенного
  светильника, решётка поверх космоса, декаль с направлением.
* **rendering** — результат грузится как YAML, `format: 7`, тайл 0 — `Space`,
  у грид-сущности есть `MapGrid` и `DecalGrid`, uid'ы не повторяются.
* **template: components load bare** — каждый компонент, который `grid_template.yml`
  пишет без полей, обязан встречаться пустым хотя бы в одной карте
  `Resources/Maps`. Это ловит целый класс ошибок «вписал компонент, а у него есть
  обязательные данные»: пустой `GridAtmosphere` роняет загрузку карты, потому что
  `TileAtmosCollectionSerializer` уходит в ветку формата 1 и требует ключ `tiles`.
  Атмосферу гриду выдаёт `AutomaticAtmosSystem`, руками её вписывать не нужно.

Проверки писались от обратного: в код по очереди вносились поломки (перевёрнутая
ось Y, транспонированный индекс чанка, выброшенный байт поворота, `wall`
вместо `dir`, отключённое наследование, переименованный прототип, turf'ы
перестали применяться первыми) — каждая обязана валить нужную проверку.
Упавшая с исключением проверка считается непройденной и печатается как `FAIL`,
а не трассировкой.

Кроме того, `convert` после записи сам декодирует чанки обратно и сверяет их с
тем, что собирался записать; отключается флагом `--no-verify`.
